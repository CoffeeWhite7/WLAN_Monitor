# 移动热点"一开就关"故障诊断报告

- 机器：LEISURE / Windows 11 专业版 26H2 (Build 26300.9974)
- 无线网卡：Intel(R) Wi-Fi 7 BE200 320MHz，驱动 24.50.0.4 (2026-05-20)
- 诊断时间：2026-11-21 10:52 – 11:08
- 结论：**不是热点/无线网卡的问题，是 Internet Connection Sharing (ICS / SharedAccess) 服务一被启用就崩溃**

## 1. 现象与复现

用 WinRT `NetworkOperatorTetheringManager` 无人值守复现，连续 11 次，11 次全中：

```
START_RESULT: Success
STATE_AFTER_2S:  On          <- 热点确实起来了
STATE_AFTER_15S: Off         <- 随即被系统关闭
AP_SSID: 校园网  BAND: Auto  AUTH: Wpa3TransitionMode
ICS_CRASH_DELTA: +1          <- 每次都伴随一次 ICS 崩溃
```

事件顺序（稳定复现）：

```
10:57:13  WLAN-AutoConfig 8005/8006  承载网络启动完成（SoftAP 已起）
10:57:15  System 7034                Internet Connection Sharing (ICS) 意外停止（第 6 次）
10:57:15  WLAN-AutoConfig 8003/8008  承载网络被停止
```

WLAN 侧无任何错误事件：8001/8006/11005/20019/20020 全部成功。**热点本身能开，是 ICS 倒下后把热点一起带走。**

## 2. 崩溃本体

Application Error 1000 / WER 1001：

| 项 | 值 |
|---|---|
| 进程 | `svchost.exe_SharedAccess` |
| 模块 | `ntdll.dll` 10.0.26100.9974 |
| 异常码 | `0xc0000008` (STATUS_INVALID_HANDLE) |
| 偏移 | `0x16a4fa` |
| 崩溃桶 | `aa92b8cc7d083934cae64a99292c2bab` |

WER 报告里的 `LoadedModule` 全是微软模块，**没有任何第三方 DLL**：

```
ipnathlp.dll, FirewallAPI.dll, FWPolicyIOMgr.dll, hnetcfgclient.dll,
hns/NSI, dhcpcsvc, wbemprox/fastprox, MSWSOCK, IPHLPAPI
```

即崩溃发生在 ICS 自己的共享配置路径（往 WinNAT/DHCP/防火墙写配置时拿到无效句柄），不是被第三方注入打崩的。

## 3. 触发条件判定：与热点无关

用 `HNetCfg.HNetShare` COM 手工开共享（Public=WLAN, Private=Radmin VPN，完全绕过 Wi-Fi Direct）：

```
ENABLE_PRIVATE_ERR: 0x80070002
ENABLE_PUBLIC_ERR : 0x80070002
ICS_CRASH_DELTA: +2
```

手工共享同样崩 ICS。**结论：只要"启用任意 ICS 共享"，ipnathlp 就崩**，热点只是最常见的那条触发路径。

随后 SharedAccess 卡在 `STOP_PENDING` 长达数分钟（`sc queryex` → PID 32308 挂死），只能 `taskkill` 掉宿主进程。这说明服务已经处于半死状态，`0x80070002` 就是这个状态的外在表现。

## 4. 根因定位：休眠恢复后的内核态陈旧句柄

时间线（决定性证据）：

| 时间 | 事件 |
|---|---|
| 11-21 10:26:16 | 承载网络 20019/20020：客户端 `FE:C7:6E:C8:75:36` 关联 + 认证成功 |
| 11-21 10:28:42 | 承载网络 20019/20020：客户端再次关联 + 认证成功 |
| 11-21 10:31:08 | 用户注销 → 10:31:10 进入睡眠 |
| 11-21 10:34:54 | Kernel-Boot 事件 + "退出新型待机"，S4 恢复（BootId 120） |
| 11-21 10:37:07 | **30 天内第一次 ICS 崩溃**（7031，第 1 次） |
| 10:39:47 / 10:39:59 / 10:41:04 | 第 2/3/4 次 |
| 11:07:16 | 第 11 次（本次诊断中复现） |

30 天回溯：`7031/7034` 里 ICS 崩溃**只有今天 10 次，之前一次都没有**；而 8006（承载网络启动成功）在 11-02 ~ 11-20 每天都有。也就是**睡眠/休眠恢复之前热点是正常的，恢复之后就废了**。

机制：S0ix/S4 恢复后 WinNAT/WFP/接口句柄在内核里被重建，而 ipnathlp 缓存的句柄已失效 → 启用共享时 `NtClose`/句柄操作收到 `STATUS_INVALID_HANDLE` → 服务被 fail-fast 杀掉。

## 6. 修复方案

**决定性动作：完整重启**（把 hiberboot 置 0 做一次冷启动最干净）。已在本机排入下次启动生效的重置：

```
netsh winsock reset      -> 已执行，需重启生效
netsh int ip reset       -> 已执行，需重启生效
netsh int ipv6 reset     -> 已执行，需重启生效
```

重启后立即验证（脚本已就位）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\asus\Documents\deepseek-harness\default-workspace\hotspot-test.ps1" -Action start -WaitSec 15
```

判定标准：`STATE_AFTER_15S: On` 且 `ICS_CRASH_DELTA: 0`。

若重启后仍崩，按顺序做：

1. 冷启动（禁用快速启动 + 关机再开）：
   `powercfg /h off` → 关机 → 开机（做完可 `powercfg /h on` 恢复）
2. 组件完整性：
   `DISM /Online /Cleanup-Image /RestoreHealth` → `sfc /scannow` → 重启
3. 网络组件全量重建（会清掉所有网卡配置，需重配）：
   `netcfg -d` → 重启
4. 更新层：本机 11-15 装过 KB5132061 / KB5132688。崩溃起点虽是 11-21 休眠恢复，但若冷启动后复发，卸载这两个补丁再验一次。

## 7. 临时规避

- 不要再走"睡眠/休眠 → 直接开热点"这条路；睡眠恢复后先完整重启一次。
- 若只是要共享网络、不在乎"移动热点"这个名字，可用 WinNAT/WSL 的 NAT，或直接用手机 USB 反向共享，绕开 ICS 引擎。

## 8. 追加：5GHz 频段热点可行性（重启后复测）

重启后 ICS 已正常，本节回答"能不能用 5GHz 热点"。

**能力层：支持。** 驱动 `netsh wlan show drivers` 报 2.4 / 5 / 6 GHz 三段；WinRT `NetworkOperatorTetheringAccessPointConfiguration.IsBandSupported()`：

```
Auto               = True
TwoPointFourGigahertz = True
FiveGigahertz      = True
SixGigahertz       = False      <- 硬件有 6GHz，但 Windows 热点 API 不支持
```

加密方式：WPA2 / WPA3过渡 / WPA3 全部 True。

**实测层：5GHz 强制起不来。**

| 频段 | 加密 | Start 结果 | 状态 |
|---|---|---|---|
| Auto | WPA3过渡 | Success | On（客户端可连） |
| 2.4GHz | WPA3过渡 | Success | On |
| 5GHz | WPA3过渡 | **WiFiDeviceOff** | Off |
| 5GHz | WPA2 | **WiFiDeviceOff** | Off |
| 5GHz | WPA3 | **WiFiDeviceOff** | Off |

**原因：不是"上游占 5GHz"，而是 DFS 信道。** 上游 QQHRIT-H3C 扫到 6 个 BSSID，全部在 5GHz（ch36 / ch44 / ch52 / ch60 / ch149 / ch149）。系统按信号强度自选，选中了最强的 **ch52（DFS 雷达信道，-34dBm）**。软 AP 不能做雷达检测，所以不能落在 DFS 信道上；而强制 5GHz 时驱动又没有可用信道 → 直接 `WiFiDeviceOff`。

**A/B 实测（同机、同 SSID、同一时刻，唯一变量 = 信道是否为 DFS）：**

| 场景 | 上游 BSSID | 信道 | 5GHz 热点 |
|---|---|---|---|
| A 系统自选 | 6c:87:20:28:15:00 | ch52（DFS） | `WiFiDeviceOff` → Off |
| B 钉非 DFS | 6c:87:20:27:e8:e0 | ch149（非 DFS） | `Success` → **On**（稳定 20s+，ICS 无崩溃） |

即：**BE200 可以同时 5GHz STA + 5GHz AP**，前提是 STA 落在非 DFS 信道（36/40/44/48 / 149/153/157/161/165）。ch52、ch60、ch100–144 属 DFS，不能作 AP。

**结论与做法（修正）**

- 5GHz 热点**能开**，条件是上游 STA 不在 DFS 信道。
- 默认会失败的原因：校园网系统自选到的 ch52 是 DFS，信号最强所以总被选中。
- 稳定用法：连上后把 STA 钉到该 SSID 的非 DFS BSSID（`wlan-pin-bssid.ps1`）。注意 BSSID 随位置变化，可先扫描再挑非 DFS 的。
- 一旦漫游回 ch52，5GHz 热点会再次失败；长期稳定需自动化（连上事件触发自动钉）。
- 6GHz 热点：本版本 Windows 热点 API 不支持（`IsBandSupported(SixGigahertz)=False`），上限仍是 5GHz。
